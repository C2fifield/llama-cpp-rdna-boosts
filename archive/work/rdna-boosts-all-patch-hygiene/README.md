## 0. The problem

`rdna-boosts-all.patch` is a documented convenience artifact: the entire 16-patch net as one patch against
the fork point. It is regenerated on every release and committed, so each release adds a new ~full-size
blob to git history. Current reality (r48, 2026-10-11):

| metric | value |
|---|---:|
| file size | **3.19 MiB** (grew from the ~1.35 MiB quoted in the 2026-09-15 note) |
| commits touching it | **194** |
| repo `.git` | **96 MiB** |
| `release.json.all_patch.sha256` | `219e3409b1312a11d4cc059fa9d53c47924f65726337614bc00651af45760247` |

It is derivable from `patches/` + `scripts/apply-all.sh`, so it is pure convenience — but it is also a
published GitHub Release asset and referenced from the repo layout.

## 1. What references it (must move if the file is untracked)

- `release.json` → `all_patch.name` + `sha256` (read by `validate-set.sh`; `validate.yml` checks it).
- `.github/workflows/release.yml` → attaches it and adds it to `SHA256SUMS`.
- `.github/workflows/validate.yml` → verifies the recorded sha256.
- `README.md` layout table (`├── rdna-boosts-all.patch  # convenience: ...`).
- `AGENTS.md` layout table.

## 2. Options (from the parked TODO entry)

- **(a) Keep as-is.** No work; the `.git` cost keeps growing.
- **(b) Stop tracking it; generate on demand** in the release pipeline / for the GitHub Release asset
  (from `patches/` + `release.json`). The layout references move to "generated by `scripts/make-release.sh`".
  This is the likely answer, but the release workout must regenerate it *before* `sha256sum` and the asset
  upload, and `validate.yml`'s check must become "regenerate and compare", not "compare the committed file".
- **(c) History rewrite** (`git filter-repo` + force-push + re-tag every `v16-*`). Measure the real
  recovery first: the patch text is already close to incompressible, so the win is bounded, and the cost is
  a force-push to a **published** repo (see the Pushing policy). Not recommended without a measured win.
