## A. Gemma4 26B-A4B front-vs-tail divergence is a near-tie (accept as MoE drift)

**Method.** `llama-cli` was instrumented (env-gated `LLAMA_DEBUG_GEN`, `common/sampling.cpp`) to print
the top-1/top-2 logits at every sampled step *inside* `common_sampler_sample`, i.e. through the same
server/chat-template path `llama-cli` actually samples from. (The prompt is a chat-templated Gemma4
request, so `llama-debug`'s raw decode is not the same context.) Instrumentation reverted after the
measurement; it is not part of either patch.

**The first four generated tokens are identical in all four arms:**
`100 <|channel>`, `45518 thought`, `107 ' '`, `236776 'A'`.

**First divergent token = step 4.** The two candidates are `122170 = " README"` and `1440 = " long"`:

| placement | `MOE_EXPERT_CACHE_MIB` | step-4 pick | logit(" README") | logit(" long") | top-2 margin |
|---|---:|---|---:|---:|---:|
| tail (default) | 4096 | ` README` | 26.588764 | 26.537333 | **0.051** |
| front (`LLAMA_HOST_EXPERTS_FROM_END=0`) | 4096 | ` long` | 26.386072 | 26.406178 | **0.020** |
| tail | 0 | ` long` | 26.417345 | 26.440115 | **0.023** |
| front | 0 | ` README` | 26.573360 | 26.312599 | **0.261** |

The (placement, cache) pair maps onto the two outputs from the README, and toggling the cache alone
flips the argmax. The deciding margin is 0.02-0.26 while the arm-to-arm logit perturbation is ~0.1-0.2
(e.g. step 0 logit1: tail+cache 25.709, front+cache 25.534, tail+nocache 25.535, front+nocache 25.625;
four distinct values) — **the picks are decided inside the noise floor.**

**Narrowing.** `-ncmoe 0` (no host experts, all device) → output B; `-sm layer -ncmoe 8` tail *and*
front → output A; both coherent, zero `////`. So the placement changes a reduction (host-vs-device MoE
kernels), and the fused/segmented host tensor (`ffn_gate_up_exps`, see B) is one place where the
serving path differs. The consequence is confined to argmax flips at near-ties.

**Conclusion / recommendation.** (A) is the benign explanation: near-tie logit drift, the same class
the MTP methodology already accepts for MoE ("sane output is the bar"; MTP gates must be long and
reasoning-pinned). **Recommend accept-as-MoE-drift and keep the r63 default (tail).** It is not a
correctness defect: no quality regression is observable, both arms are coherent, and the 35B is
bit-identical. Document it in the r63/next `WORKLOG` entry as a known model-specific near-tie flip.

No fix is proposed for (A).

## B. Segmented `set_tensor_async` classifier — root cause, caller, and a real fix

### Instrumentation result (the missing fact)

`ggml_backend_meta_set_tensor_async` (env `GGML_META_ASYNC_TRACE`) on a rear `-ncmoe 20` 35B-A3B Q8_0
`llama-bench -p64 -n4`:

* **6548 calls, all `nseg=1 nr0=1`** — the segmented branch is **never** entered on 35B. The caller is
  the scheduler's `ggml_backend_sched_copy_input` → `copy_experts`, range `n*expert_size (+min(512,…))`.
* The 35B's host experts are the separate `ffn_gate_exps`/`ffn_up_exps`/`ffn_down_exps` (single-segment).

**Gemma4 `-ncmoe 8` does exercise it:** `blk.22..29.ffn_gate_up_exps.weight`, `axis=1`,
`nseg=1, nr[0]=2`, `row_stride = nb[2] = 2230272`, also via `copy_experts`. On the current tree every
call has `size % row_stride ∈ {0, 512}` (the scheduler's MMQ tail), so the reverted
`size % row_stride <= 512` heuristic would **not** have diverted any of them. The hang it caused was on
the **pre-loader-guard** tree, where the loader's 1 MiB chunks reached the segmented branch; the r63
Meta whole-tensor loader guard removed those calls.

### The latent defect (still real for any other caller)

The classifier `offset % row_stride == 0` checks only the offset. A range that starts row-aligned but
is neither a whole number of rows nor a ≤512 tail is misrouted to the old sync splitter, which:
axis 0 → `GGML_ASSERT(size % row_stride == 0)` abort; axis 1 → writes `size % row_stride` bogus bytes
into the next expert slot.

### Fix (direction 1 — partial-row writer in the sync splitter)

Patch: `tools/meta-async-partial-row-fix.patch` (`ggml/src/ggml-backend-meta.cpp`, for block 09).

* `ggml_backend_meta_buffer_set_tensor`'s **segmented** axis-0/axis-1 paths now accept an arbitrary
  `[offset, offset+size)` range: head partial row + full rows (the existing strided 2-D copy per
  segment chunk) + tail partial row, mirroring `write_partial_row` of the non-segmented path.
* `ggml_backend_meta_set_tensor_async`'s segmented branch now **always** forwards to that sync setter
  and the whole-tensor accumulator is deleted. There is nothing to classify, so the unsound predicate
  (and the accumulator that stranded a partial per-op range) are both gone.

### Validation (both fixes, guard on = delivery config)

| 35B `llama-bench -ncmoe 20 -p64 -n20` ×5, `-lm auto` | rc=0 all (tg20 ≈ 41 t/s), no `exit=124` |
| 35B same ×5 and ×16, `-lm none` | rc=0 all |
| Gemma4 4 `(placement, cache)` arms | **bit-identical** to the r63 table (`0d2717074ba2`/`468a953af132`) |
| 35B coherence (`-ncmoe 20`) | coherent, no `////` |

## B-extra. The loader-async path (guard removed) — crash fixed, plus a second latent bug

Removing the r63 Meta loader guard (`-lm none`, so the loader drives `set_tensor_async` with 1 MiB
chunks) exposes both:

1. **Pre-fix: 15/15 abort** at `ggml-backend-meta.cpp:1783 GGML_ASSERT(size % row_stride == 0)`
   (the axis-0 segmented sync splitter, via the classifier). **The meta partial-row fix removes it.**
2. **Post-fix, rare: `hipEventSynchronize` "unknown error"** in
   `ggml_backend_cuda_set_tensor_2d_async` (`ggml-cuda.cu:3839`), stack
   `sched_copy_input → meta set_tensor_async → cuda set_tensor_2d_async` (the non-segmented switch, not
   the code change #1). Rate ≈2/39 guard-off runs; guard-on was 24/24 clean. `GGML_CUDA_SPLICE_GATHER=0`
   is 20/20 clean ⇒ the pinned splice-gather ring.

   **Cause:** the ring was a function-local `static thread_local`, while the loader's `-lm none` uploader
   builds its own temporary Meta backend (and CUDA contexts) and frees them after the load. The ring's
   `hipEvent`s were recorded on those now-destroyed streams, and the decode's next slot reuse failed.

   **Fix (blocks 10):** `tools/splice-gather-ring-owner-fix.patch` — move the ring into
   `ggml_backend_cuda_context` (one context == one device) and free its events/pinned buffers in the
   context destructor, before the streams. Guard-off then 24/24 clean; guard-on 16/16 clean.

   This is a genuine latent bug, but **the delivery never hits it** because the r63 loader guard keeps
   the Meta device off the loader async path. It matters only if that guard is ever removed (e.g. the
   sibling `wip/meta-segmented-upload-async` campaign). Recommend folding it in together with that, as a
   block-10 amendment.
