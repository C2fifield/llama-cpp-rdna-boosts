Thanks — the harness detail (8 interleaved pairs, alternating order, fresh server per arm, plus a null
A/B) is what made this worth chasing, so we reproduced your comparison as closely as we could here and
tried to break it.  The short version: **on our box the two builds are equal within noise (<= 0.4 %, and
the sign is not stable), and the compiled-code difference between them is 224 bytes.**  Details, then
three diagnostics that would settle it on your side.

**Why we think the change cannot be a 3.5 % effect.**  For your config the two builds are the same
program: the `[TAG_META_UNALLOC_ALIAS]` path only runs for a tensor in the split-state walk with **no
buffer of its own**, and on r80 that tensor asserted in `ggml_backend_meta_buffer_n_bufs` — so every
graph that ran on r80 never reached it (that is also why you never saw the assert: it is not that the
new path is inert, it is that on r80 the case is unreachable without crashing).  So all that is left is
codegen, and we measured that directly with the exact `ggml-base` flags (`-O3 -DNDEBUG`), on both the
ROCm 10.0 clang you use and 10.1:

| | r80-shaped meta | r82 meta |
|---|---|---|
| `.text` of `ggml-backend-meta.cpp.o` | 82 633 B (10.0) / 82 681 B (10.1) | 82 857 B / 82 905 B |
| `get_split_state(const ggml_tensor *, bool)` | 385 B, out of line | 454 B, out of line |
| `get_split_state(stc &, const ggml_tensor *, bool)` | 4 121 B / 4 137 B | 4 249 B / 4 265 B |

So: +224 B, **no inlining change in either arm** (the dispatcher is out of line in both, so the call
structure is identical), and the only hot-path difference is one `buffer == nullptr` test plus the
classification being evaluated from a hoisted local.  One caveat on the profile: `perf` attributes
samples to whichever symbol holds the PC, so when a function's prologue/branch layout shifts, samples
move between `init_tensor_impl` and `get_split_state` without any extra work happening — the
`+26 %/+31 %/+40 %` triple is exactly that shape (all three are the same recursion).  We could not turn
it into wall time.

**How we measured (and one pitfall that bit us first).**  2x R9700, gfx1201, ROCm 10.1, r86-candidate
tree; only `libggml-base.so.0.26.0` is swapped between arms, like your setup.  Config matched to yours
as closely as our model set allows: `Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS` + the shared Q8_0 MTP head,
`-sm tensor -ncmoe 47 -fa auto -ctk q8_0 -ctv q8_0 -c 131072 -b 2048 -ub 2048 -t 8 -np 4 --fit off
--load-mode none --lazy-mode off --spec-type draft-mtp-adaptive --spec-draft-n-max 3`, four concurrent
greedy `/completion` requests (`n_predict 192`), aggregate tokens/wall.

The pitfall, in case it affects your harness too: if the four prefills are left inside the measurement
window, the four decode streams do **not** overlap for the whole window — the server starts decoding a
slot as soon as its prefill finishes, so the per-step cost depends on how many streams happen to be
decoding.  Left that way, the *same* build gave us 63.8 / 63.8 / 63.8 / **139.2** t/s, a 2.2x
bimodality (all four slots report a constant ms/token within a run, so it is batch composition, not
drift).  Pre-warming each slot's prompt (`cache_prompt`, one `n_predict: 1` request per slot) and then
firing the four measured requests gives pure decode and reproduces to **0.1-0.3 %** within an arm.

**Result** (paired, arms alternating, fresh server per arm):

| session | pairs | r82 meta | alias reverted | paired |
|---|---|---|---|---|
| 1 | 2 | 99.87 t/s | 99.63 t/s | +0.24 % |
| 2 | 4 | 99.39 t/s | 99.77 t/s | -0.39 % |
| 3 | 4 | 100.22 t/s | 100.24 t/s | -0.02 % |

Greedy text identical in every run (all 16 of a session hash the same).  The *same* `.so` drifts 0.8 %
between sessions here (99.39 -> 100.22), which is why we only trust same-session pairs — and it is also
why your two sessions giving 154.86 and 157.25 for the r82 arm, and the 1.5 % "one outlier pair" in the
partial revert, made us suspicious of a per-session component in the 3.5 %.

**The null result is calibrated, not just a ceiling.**  A host-path null only means something if the
instrument could have seen your effect, so we pessimised the hot dispatcher on purpose (a `volatile`
add-loop at the top of every call, nothing else changed): 100 iterations (~120 ns/call) cost **+0.23 %**,
1000 iterations (~1.2 us/call) cost **+1.17 %** -- linear, so the harness resolves host-path cost to
~0.2 %, and 3.5 % would look like ~3000 iterations per call (~350 ns on each of the ~10k lookups a step
does).  The r82 delta is one null test per call.  Our per-step time is also 1.5x yours (102 ms vs ~70 ms
at mean draft length 2.8), i.e. host cost weighs *more* here, not less.

We also checked your two hypotheses directly.  (a) *The early path is not what runs* — agreed, see
above.  (b) *"How the function compiles or recurses now"* — the recursion is unchanged and the
dispatcher did not start or stop being inlined.  And the two things your profile predicts, on our side:
the verify graphs are **not** re-allocated each step (a pre-warmed 4-stream request reports `graph
reallocs = 1 / 1 (same size) / (changed size)`), and disabling the r84 graph-layout fingerprint
entirely is worth -0.07 % (noise), so graph identity across parallel sessions is also not paying here.

**Three things that would settle it, if you are willing:**

1. `nm -C -S libggml-base.so | grep ggml_backend_meta_get_split_state` on both builds.  If one arm
   inlined the dispatcher and the other did not, that is the whole effect and it is compiler-specific —
   we would then want to know so we can force the shape.
2. The per-request counters the release already prints: `graphs reused = N` and
   `graph reallocs = N / M (same size) / (changed size)`, for both arms on the same 4-stream workload.
   With `-v` on the server you also get the `ggml_gallocr_needs_realloc` reason
   (`graph topology changed (fingerprint mismatch)` etc.).  Those two lines tell us whether the extra
   host time in your profile is per step, per request, or once.
3. A layout control: build the **same** source twice with a harmless perturbation (e.g. r80's meta file
   with an unused static function of a different size), and A/B those two arms against each other.  If
   two functionally identical builds differ by ~3 % on this workload, the delta you measured is
   layout/alignment, not the algorithm — which is the most likely explanation we have, given the 224
   bytes, but it is your box and your stack, so it is worth one session.

If the effect does reproduce on your side we have a ready shape for it: the pre-#170 hot dispatcher
exactly as it was, with the whole alias/host resolution moved into a `noinline, cold` helper.  We built
and measured that here — it is worth -0.06 % (i.e. nothing measurable), so we have not shipped it; we
would cut it the moment your numbers say the hot path matters, because it keeps the #170 fix intact and
is a pure code motion.

One separate thing we hit while setting this up, in case it is useful to you: on two devices `gemma4`
**dense** (12B Q8_0) under `-sm tensor` with `-ctk q8_0` aborts at the warmup decode —
`unsupported mul_mat split states: src0=#attn_inp_k_rot#0 axis=10 src1=Kcur_pos-5 (reshaped) axis=0`
(`ggml-backend-meta.cpp:900`).  `attn_inp_k_rot` is the K-rotation matrix, so it is the rotated-cache
type that reaches an unsupported split state; f16/bf16 K/V are fine.  That one is ours to fix and is
tracked separately (TODO #68), not part of this report.
