A/B) is what made this worth chasing, so we reproduced your comparison as closely as we could here, and

## What the two builds actually differ by

For your config they are the same program.  The `[TAG_META_UNALLOC_ALIAS]` path only runs for a tensor in
the split-state walk with **no buffer of its own** — and on r80 that tensor hit the
`ggml_backend_meta_buffer_n_bufs` assert, so no graph that ever ran on r80 reached it (that is also why
you never saw the assert: it is not that the new path is inert, it is that on r80 the case is unreachable
without crashing).  All that is left is codegen, so we measured that directly, with the exact `ggml-base`
flags (`-O3 -DNDEBUG`), on both your clang (ROCm 10.0.0) and ours (10.1.0):

| | r80-shaped meta | r82 meta |
|---|---|---|
| `.text` of `ggml-backend-meta.cpp.o` | 82 633 B (10.0) / 82 681 B (10.1) | 82 857 B / 82 905 B |
| `get_split_state(const ggml_tensor *, bool)` | 385 B, **out of line** | 454 B, **out of line** |
| `get_split_state(stc &, const ggml_tensor *, bool)` | 4 121 B / 4 137 B | 4 249 B / 4 265 B |

So: **+224 B**, **no inlining change in either arm** (the dispatcher is out of line in both, so the call
structure is identical), and the only hot-path difference is one `buffer == nullptr` test plus the
classification being evaluated from a hoisted local.  One note on the profile: `perf` attributes samples
to whichever symbol holds the PC, so when the prologue/branch layout of a recursive walk shifts, samples
move between `init_tensor_impl` and `get_split_state` without any extra work being done — your
`+26 %/+31 %/+40 %` triple is exactly that shape (all three frames are the same walk).  We could not turn
it into wall time.

## How we measured (and a pitfall that bit us first)

2x R9700, gfx1201, ROCm 10.1, r86-candidate tree; only `libggml-base.so.0.26.0` is swapped between arms,
like your setup.  Matched as closely as our model set allows: `Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS` + the
shared Q8_0 MTP head, `-sm tensor -ncmoe 47 -fa auto -ctk q8_0 -ctv q8_0 -c 131072 -b 2048 -ub 2048 -t 8
-np 4 --fit off --load-mode none --lazy-mode off --spec-type draft-mtp-adaptive --spec-draft-n-max 3`,
four concurrent greedy `/completion` requests (`n_predict 192`), aggregate tokens / wall.  (`--load-mode
none --lazy-mode off` so the PLE weights are RAM-resident and the measurement is not a page-cache race.)

The pitfall, in case it affects your harness too: if the four prefills sit inside the measurement window,
the four decode streams do **not** overlap for the whole window — the server starts decoding a slot as
soon as its prefill finishes, so the per-step cost depends on how many streams happen to be decoding.
Left that way the *same* build gave us 63.8 / 63.8 / 63.8 / **139.2** t/s, a 2.2x bimodality (all four
slots report a constant ms/token inside a run, so it is batch composition, not drift).  Caching each
slot's prompt first (`cache_prompt`, one `n_predict: 1` request per slot) and then firing the four
measured requests gives pure decode and reproduces to **0.1-0.3 %** within an arm.

## Result (paired, arms alternating, fresh server per arm)

| session | pairs | r82 meta | alias reverted | paired |
|---|---|---|---|---|
| 1 | 2 | 99.87 t/s | 99.63 t/s | +0.24 % |
| 2 | 4 | 99.39 t/s | 99.77 t/s | -0.39 % |
| 3 | 4 | 100.22 t/s | 100.24 t/s | -0.02 % |

Greedy text identical in every run (the four streams share one content hash, identical across all runs of
a session).  The *same* `.so` drifts 0.8 % between sessions here (99.39 -> 100.22), which is why we only
trust same-session pairs — and it is also why your two r82 measurements (154.86 and 157.25) and the single
+9.6 % pair in the partial revert made us suspect a per-session component in the 3.5 %.

Control arms, same session discipline: the pre-#170 hot dispatcher restored (all alias/host resolution in
a `noinline, cold` helper) **-0.06 %**; the r84 graph-layout fingerprint disabled **-0.07 %**; the pristine
delivery build **-0.05 %**.

## The null is calibrated, not just a ceiling

A host-path null only means something if the instrument could have seen your effect, so we pessimised the
hot dispatcher on purpose — a `volatile` add-loop at the top of every call, nothing else changed:

| arm | added work per call | paired vs baseline |
|---|---|---|
| 100 volatile increments | ~100 loop iterations | **+0.23 %** |
| 1000 volatile increments | ~10x that | **+1.17 %** |

So the harness resolves host-path cost at ~0.2 %; **3.5 % is about 3x the 1000-increment arm**, whereas
the r82 delta is one branch per call — roughly 1 % of what the 100-increment arm adds per call, i.e. two
orders of magnitude below the floor.  Our per-token decode is also 1.4x yours (36.9 ms/token/stream vs
~25.8 from 4 x 155 t/s), so host cost weighs *more* here, not less.

## Your two hypotheses, checked

* *"The early path itself is probably not what runs"* — agreed (see above).
* *"It may be how the function compiles or recurses now"* — the recursion is unchanged and the dispatcher
  neither started nor stopped being inlined.
* *"The verify graphs appear to be re-allocated each step"* — with cached prompts they are not: a
  pre-warmed 4-stream 192-token request reports `graph reallocs = 2 / 2 (same size) / (changed size)`
  against `graphs reused = 72`.  (With the raw harness and 512-token ubatches, i.e. varying prefill
  batches, it is 10-12 same-size per request.)  That counter is the delivery's own
  (`llama_context::sched_graph_realloc`), and `-v` on the server also prints the
  `ggml_gallocr_needs_realloc` reason, `graph topology changed (fingerprint mismatch)` etc.
* *Graph identity across parallel sessions* — disabling the r84 layout fingerprint entirely is worth
  -0.07 %, so it is not paying on this workload either.

## What would settle it on your side

1. `nm -C -S libggml-base.so | grep ggml_backend_meta_get_split_state` on **both** builds.  If one arm
   inlined the dispatcher and the other did not, that is the whole effect and it is compiler-specific —
   we would want to know, so we can force the shape.  (Both your binaries are the same clang we tested
   with, so on our side it is out of line in both.)
2. The per-request `graphs reused = N` and `graph reallocs = N / M (same size) / (changed size)` lines
   from both arms on the same 4-stream workload.  Those tell us whether the extra host time in your
   profile is per step, per request or once, which is the difference between "the walk got slower" and
   "the walk runs more often".
3. A **layout control**, because that is our leading explanation for a 3.5 % delta from 224 bytes: build
   the same source twice with a harmless perturbation (e.g. r80's meta file plus an unused static
   function of a different size) and A/B those two arms against each other, 8 pairs.  If two
   functionally identical builds differ by ~3 % on this workload, the delta is code layout/alignment.
   The cheapest version: rebuild each arm once more and re-run the same 8 pairs — if the sign follows
   the build (or the session) rather than the source, that is the same conclusion.
4. If you can afford it: 16 pairs on the partial revert with its own null-A/B spread reported for the
   same session, and one arm on `-sm layer`.  If the effect is the Meta split-state walk, `-sm layer`
   should not show it (the meta backend is not in that config); if it does show it, we are looking at
   something on the common path instead.

## One separate thing we hit, in case it is useful to you

On two devices, `gemma4` **dense** (12B Q8_0) under `-sm tensor` with `-ctk q8_0` aborts at the warmup
decode: `unsupported mul_mat split states: src0=#attn_inp_k_rot#0 axis=10 src1=Kcur_pos-5 (reshaped)
axis=0` (`ggml-backend-meta.cpp:900`).  `attn_inp_k_rot` is the K rotation matrix, so the rotated-cache
type reaches an unsupported split state; f16/bf16 K/V are fine.  That one is ours to fix and is tracked
separately — not part of this report.
