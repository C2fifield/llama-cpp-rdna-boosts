# `moe-layer-stagger` findings — 2026-10-14

**Verdict: the stagger hypothesis is REFUTED.**  With the page-cache confound removed, **which** MoE
layers are host-resident has **no effect** on prefill at a fixed host-byte count (four disjoint host
sets within 0.1 %).  Partial-offload prefill here is bound by the H2D path, not by the upload *schedule*,
so neither a by-ratio spread nor a deeper ring pipeline can help: the bytes still have to cross the same
link.  Separately, the chosen basis (`-sm tensor` + `-ncmoe`) is on a **corrupt** path (§4) — that must
be settled before any further partial-residency perf work.

All numbers: 2× R9700 gfx1201, ROCm 7.14.1, `~/llama.cpp/build-rocm-hybrid` (delivery tip
`7f15fb91d`, r61), `-ngl 99 -sm tensor -ncmoe N -fa 1 -b 4096 -t 8`,
`llama-bench -p … -n 0 -r 2..3`, `MOE_EXPERT_HEATMAP=0` (and `MOE_EXPERT_CACHE_MIB=0` where noted).
Raw logs: `logs/`.

## 0. Measurement method (do this first — it is a hard confound)

Run from a **tmpfs copy of the model**, not the disk-backed one.  On the first pass the prefill numbers
climbed **1168 → 1500 t/s (+28 %)** monotonically across ~30 min of runs, and that trend is larger than
any effect being measured.  `fincore` showed shard 1 fully resident but the PLE shard only 22.2 G of
26.8 G.  Copying both shards to `/tmp` (tmpfs) and dropping the originals' page cache
(`posix_fadvise(POSIX_FADV_DONTNEED)`) makes repeat runs identical to <0.1 %.  **The original
"stagger wins +12 %" reading was entirely this warm-up.**

Harness: `tools/run-stagger-bench.sh <tag> <ncmoe> <layer-list|-|>` (the `-ncmoe` count is forced to the
list length, because the count is still consumed by the MoE-cache preflight even though the loader uses
the override list).  Knob patch: `tools/ncmoe-layer-select.patch` (env-gated `LLAMA_NCMOE_LAYERS` /
`LLAMA_NCMOE_STRIDE` / `LLAMA_NCMOE_OFFSET`; inert unless set).

## 1. Stagger is a no-op (ncmoe 24, ub 2048, /tmp)

| host set | pp4096 | pp8192 |
|---|---:|---:|
| contiguous `0..23` | 1578.8 | 1640.3 |
| even `0,2,..,46`   | 1576.8 | 1640.5 |
| odd `1,3,..,47`    | 1578.8 | 1640.9 |
| contiguous `24..47`| 1578.6 | 1640.6 |

Four disjoint sets, identical to 0.1 %.  (An interleaved A/B/A/B reproduced this.)  **Layer *order* is
irrelevant to prefill.**

## 2. The cost is the H2D of the whole host table, per ubatch

| ncmoe (host layers) | pp4096 | pp8192 |
|---|---:|---:|
| 0  | 3007.6 | 3023.1 |
| 12 | 2058.9 | 2133.3 |
| 24 | 1573.2 | 1633.2 |
| 36 | 1212.5 | 1255.9 |
| 48 |  979.8 | 1031.1 |

Marginal cost ≈ **52–67 ms per host layer per ubatch**: `ncmoe 24` re-uploads 24 × 912.5 MiB = 21.4 GiB
per ubatch, i.e. ~15–18 GB/s effective.  The GPUs sit behind a PCIe switch whose **upstream link is
x4** (`01:00.0` / `04:00.0` / `07:00.0` and root port `00:01.1` all `32 GT/s x4`), so this is close to
the link.  Because the bytes/token scale as `1/ub`, the *config* lever is ubatch width, not placement:

| `-ub` | pp4096 | pp8192 | pp16384 |
|---|---:|---:|---:|
| 2048 | 1575 | 1636 | 1642 |
| 4096 | 2152 | 2167 | 2183 |
| 8192 | 2154 | 2167 | 2184 |

**+37 %** from `-ub 2048 → 4096` at the same `-ncmoe 24` (ub 8192 is capped by `-b 4096` here).  The
other lever is moving *fewer* bytes: whole-table staging re-uploads all 512 experts/ubatch, whereas the
device gather would move only the routed ones — but see §4 and the gather's documented
destination-reuse bug (`WORKLOG.md` 261003.001 "Hole B").

Note `-sm tensor -ncmoe 24` staging **on** (default, ~1575) vs **off** (`GGML_SCHED_STAGE=0`, ~2892 in
llama-bench) inverts the x16-era result the default was fitted to; the width gate
(`sched_stage_min_tokens`, ~1536 at 14.5 GB/s) and the copy-vs-stage decision look mis-calibrated for
this x4 + `-sm tensor` case.  **Not yet investigated** — and it must not be chased until §4 is settled,
since the two paths differ in correctness here.

## 3. The answer to "does the ring prefetch ahead?"

No.  `ggml_backend_sched_compute_splits` (`ggml-backend.cpp:2887`) walks splits in topological order and
issues split N's host-weight upload at the **top of split N's own iteration** (`sched_stage_issue`
`:2903`; for `-sm tensor` the meta `stage_input` runs during split N's input copy, `:2640`, issuing the
per-device H2D on the aux copy stream in `ggml_backend_meta_stage_input`, `ggml-backend-meta.cpp:2521`
at `:2616-2633`).  Split N−1's compute was enqueued in the previous iteration (`:2929`).  So the upload
**overlaps the previous split's in-flight compute** (one split deep) but does **not** lead it, and there
is no split N+1 prefetch.  A "fill the ring for layers N+4..N+7 before N..N−3" schedule does not exist
today; it would be new code.  And it cannot help while the link is the binding constraint (§2): the same
bytes cross the same link regardless of when they are issued.

## 4. BLOCKER — `-sm tensor` + host experts is corrupt in the default path

`llama-cli`, long prompt (`prompts/prose-rdna-boosts.txt`, `--seed 42 --temp 0 -fa 1`):

| model | config | output |
|---|---|---|
| 35B-A3B Q8_0 | `-sm tensor -ncmoe 20` | `33333333333333333333…` |
| 35B-A3B Q8_0 | `-sm tensor -ncmoe 0` | coherent |
| 35B-A3B Q8_0 | `-sm layer -ncmoe 20` | coherent |
| gemma4 26B-A4B Q4_K_XL | `-sm tensor -ncmoe 20` | `<unused32><unused32>…` |
| gemma4 26B-A4B Q4_K_XL | `-sm tensor -ncmoe 20` + `GGML_META_SPLIT_COPY=0` | coherent |
| Flash-Next GSQ-IQ3_XXS | `-sm tensor -ncmoe 24` (staging on) | `33333333…` |
| Flash-Next GSQ-IQ3_XXS | `-sm tensor -ncmoe 24` + `GGML_SCHED_STAGE=0` | coherent |

`llama-perplexity` is worse: `[1]nan … [8]nan`, `Unexpected negative standard deviation of log(prob)`
for 35B-A3B and gemma4 at `-ncmoe 4/8/20/40/99`, 2 and 3 GPUs.

* **Isolated the unit**: `GGML_META_SPLIT_COPY=0` (mirrored) is coherent, `=1` (the **default**,
  `src/llama-model.cpp:410`) is garbage → the **Meta split copy of the host-resident expert weights**.
* **Not** the heat map (`MOE_EXPERT_HEATMAP=0` and default both fail; no sidecar), **not** the expert
  cache (`MOE_EXPERT_CACHE_MIB=0` and auto both fail), **not** `--lazy-mode` (`off` fails), **not** the
  load mode (`auto`/`mmap` fail).
* **Not a regression**: `build-r55-ref` (pre-r60) fails identically, so it long predates the heat map.
* **Partially known**: `TODO.md` #53 (35B `-sm tensor -ncmoe` impurity) was declared resolved in r41,
  but that covered a near-tie bit-flip, not gross corruption; the r56 note already documents a related
  `ggml-backend-meta.cpp:1781 GGML_ASSERT(size % row_stride == 0)` for Flash-Next
  `-ncmoe 48 -sm tensor`.
