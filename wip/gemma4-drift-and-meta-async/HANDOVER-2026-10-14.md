## 0. Why this campaign exists

The r63 promotion (`moe-upload-overlap`, folded into blocks 09/10) left two residuals:

* **Gemma4 26B-A4B front vs tail greedy text differs** (both coherent; near-tie drift suspected but not
  proven).  r63 shipped with this accepted as MoE drift.
* **`ggml_backend_meta_set_tensor_async`'s segmented mid-row fast path** only checks `offset`, not
  `size`, so a mid-row chunk is misrouted to the sync splitter (axis-0 assert / axis-1 bogus tail).  The
  r63 loader guard makes it unreachable *from the loader*; the classifier is still wrong.  A heuristic
  fix was tried and **hung the rear placement**; it was reverted.

## 4. Hypotheses to discriminate

**A (Gemma4 drift).**
1. It is a genuine near-tie: the divergent token's top-2 logit margin is ~0.  → document, accept.
2. It is a placement-dependent reduction: the host-expert upload path (op-offload pruned upload, cache
   identity-vs-remap) changes a kernel/reduction order even at full residency.  → find the kernel.
3. It is cache-state-specific (the arena's identity fast path serves the whole table vs the remap path
   serving slots).  → compare `MOE_EXPERT_CACHE_MIB` auto/0/4096 with logits, not hashes.

**B (meta async).**
1. The scheduler's per-op range is always `n*expert_size (+≤512 tail)` — then the classifier can key on
   `expert_size`, not the row stride.  → instrument and confirm.
2. Some caller sends an aligned-`offset`, mid-row-`size` range that the heuristic diverted.  → the
   instrumentation in §Fix directions will name it.
3. The accumulator's flush condition (`offset+size == total`) is the real defect — a per-split flush
   makes any classifier safe.  → decide the contract with the scheduler/meta owners.

## 5. Pitfalls

* **Do not repeat the heuristic fix** (`size % row_stride <= 512`): it hangs.  The patch is in
  `tools/meta-async-fastpath-attempt.patch` for reference only.
* **Changing `llama_model_params` requires a full rebuild of every tool** — a stale `llama-perplexity`
  segfaulted during the r63 work because its object still used the old struct-by-value layout.  Use
  `cmake --build <dir> -j` (all targets), not just `llama-cli`.
* MoE output is **not** required to be bit-identical (MTP methodology); judge A at the **logits** level.
* `blk.39` (35B) is a full-attention layer, not dense; Gemma4's tail `blk.22-29` is verified correct via
  `GGML_STAGE_TRACE=1` (`NCMOE_TAIL host blk.<i>`).
* Never apply `wip/`/`archive/work/` to the fork; the delivered form is `patches/`.
