# wip/async-input-graph-ordering — session findings (2026-10-19, after r89)

Raw record of the first debugging session.  `README.md` carries the claims and the current plan; this
file keeps the measurements and the ruled-out list so they are not re-derived.

Build: r89 + `tools/DEBUGBUILD.patch` (`~/llama.cpp` branch `ain-debug`, `BUILD_DIR=build-ain`).
Instrument: `llama-perplexity --kl-divergence-base` self-comparison (same binary, two fresh processes),
4B Q8_0 unless noted, `-c 512 --chunks 12|24 -ub 8 -b 8 -ngl 99 -fa on -t 8 -ctk/ctv q8_0`,
gfx1201 one card, ROCm 10.1.  `same top p 99.967-99.984 %` is the noise floor (= deterministic);
anything in the 85-98 % band is divergence.  Run-to-run spread of a divergent arm is ~1.5 points, so
only the floor vs. the band is meaningful.

## What is established

1. **The async uploads are ordered.**  `AIN_VERIFY` enqueues a D2H of each upload destination on the
   *compute* stream immediately after `ggml_cuda_async_input_wait()` (i.e. exactly where the graph's
   first read happens) and compares it with the bytes the host uploaded.  With no intervening device
   sync (`AIN_DUMP_EVERY=1500`): **1024 snapshots, 0 mismatches**.  The earlier "the copy lands after
   the read" reading of the sleep result is therefore wrong.
2. **HIP's primitives are fine.**  Two standalone reproducers (`tools/ain_hip_test.cpp`,
   `tools/ain_hip_test2.cpp`, build line in the file header):
   - a copy on `hipStreamPerThread` + `hipEventRecord` + `hipStreamWaitEvent(compute)` before
     `hipGraphLaunch` is ordered correctly, with and without an explicit upload stream;
   - an event recorded on the compute stream *after* `hipGraphLaunch` covers the replay's execution,
     including a ~100-300 us graph with the host running 5-7x ahead (the `done_ev` guard works);
   - the two must be combined (copy waits for the previous graph's `done_ev`, graph waits for the
     copy's `ev`) — either guard alone is exactly the "no guard" failure mode.
3. **The bookkeeping is consistent.**  `AIN_TRACE` over a run: `wait` found `pending == true` on every
   call (`nopend = 0`), one thread, one stream pair, ~9.5 uploads per graph, `done_ev` waited on every
   copy after the first 10.  `hipEventQuery(done_ev)` at upload time returned *complete* on 14227/14227
   uploads — i.e. **consecutive graphs do not overlap in this workload at all.**
4. **The per-graph host writes are all ordered.**  Tensor histogram over a run (async path):
   `inp_mixed_embd` (82 KiB), `inp_mixed_slots`, `rs_s_copy`, `inp_pos`, `attn_inp_k_rot` (262 KiB),
   `attn_inp_v_rot` (16 KiB), `attn_inp_k_idxs`, `attn_inp_v_idxs`, `attn_inp_kq_mask`, `out_ids`;
   plus `ggml_backend_cuda_set_tensor_2d_async` twice per graph (the splice-gather, on the main stream).
   `cpy_tensor`, `cpy_tensor_async`, `get_tensor`, `get_tensor_2d` and `buffer_clear` are **not** used in
   the loop; the 426 `set_tensor` sync-path calls are **model-weight loads at startup** (names logged).
5. **Not GDN, not the fusions, not the MoE.**  Dense `Qwen3.8-27B Q4_K_M` diverges exactly the same
   (96.2 % vs 100.000 %); `GGML_CUDA_GDN_CHUNKED=0` and `GGML_CUDA_GDN_GATHER_INDEX=0` change nothing;
   `GGML_CUDA_DISABLE_FUSION=1` still diverges (97.4 %).
6. **Not the r25 graph-lifetime machinery.**  `GGML_CUDA_GRAPH_MEM_GEN=0` (96.6 %) and
   `GGML_HIP_GRAPH_FORCE_UPDATE=1` (96.0 %) both still diverge.
7. **It is global host speed, not a window.**  A host delay *before* the graph launch
   (`AIN_SLEEP_US=20/50/100/300/1000`) and a delay *after* the launch (`AIN_SLEEP_LAUNCH_US=50/300`)
   both land on the floor.  `AIN_SYNC_SET` (copy complete at issue), `AIN_SYNC_COPY`,
   `AIN_SYNC_COMPUTE`, `AIN_SYNC_DEVICE` and `AIN_SYNC_INPUTS` (sched synchronize before `set_inputs`
   on the graph-reuse path) all land on the floor.  What they share is only "the host runs slower" —
   so none of them is a diagnosis.
8. **Not the per-thread default stream.**  `AIN_EXPL_STREAM=1` (uploads on an explicit non-blocking
   stream) still diverges (97.3 %).
9. **Graphs are required.**  `GGML_CUDA_DISABLE_GRAPHS=1` and `GGML_CUDA_DISABLE_VERIFY_GRAPHS=1`
   (which stops capturing the <= 8-token band) are both deterministic; `-ub 512` (no capture) is
   deterministic; `-ub 8` and `-ub 1` diverge at `n_seq = 1`.
10. **Batching/lazy widen it** (as recorded in r89): `ASYNC_INPUT=1` 93.8-97.4 %, with `BATCH=1`
    84.9-90.4 % at `-ub 1`.   They are amplifiers, not the cause.

## What the divergence looks like

`AIN_GRAPHSUM` records a 64-byte checksum of each graph's last OUTPUT tensor (`result_output`), D2H'd on
the compute stream with no host sync.  Two runs of the same binary:
- run A vs run B: 42 of 299 graphs differ, in two hunks — indices **97..128** (32 consecutive graphs)
  and **289..298** (the last 10).  Everything between them is identical, i.e. the difference does not
  propagate (a prefill KV write that diverged could not re-converge; a *logits-row* difference can).
- a repeat pair of runs with the same instrumentation was **identical** (0 differences), and the graph
  kinds/node counts always agree — the instrumentation itself perturbs the race.

That, plus (3) — no inter-graph overlap — leaves **inside a single graph's execution** as the only place
the difference can be produced, and points at the one per-graph structure that is not covered by CUDA
stream order.

## Current best hypothesis (session 2026-10-19)

`ggml_backend_sched` reports `graph: nodes = 2025, splits = 2, input objects = 4, input tensors = 12`
and `graphs reused = 61` for this workload on **one** GPU: the graph is split across the CUDA backend and
a second (CPU-side) split.  A cross-backend split is consumed through the scheduler's
backend-event record/wait pair, which is the one "host must wait for the card" signal in the path that
is *not* the async input ring.  Two candidates, both cheap to test:

- **H-A (top):** the second split reads the first split's output before the CUDA graph has produced it
  (the scheduler's event record/wait for a *captured* graph is not covering the replay, or the consumer
  is a host read of a pinned output tensor).  This would be invisible to every CUDA-side instrument
  above, would be fixed by any host delay, and would explain why the *delivery default* (blocked host)
  never sees it.
- **H-B:** an in-graph race between the two streams the graph itself may contain (the fork/join path,
  `try_launch_concurrent_event`).  Not observed in the 4B run (`-lv 4` shows no "Launching N streams"),
  so it is unlikely for this reproducer but must be checked on the MoE/MTP configs.

Test plan for H-A: identify split 2 (`sched_reserve` / `GGML_SCHED_DEBUG`, or print
`sched->splits[i].backend->get_name()` in the fork); then instrument
`ggml_backend_cuda_event_record` / the scheduler's `ggml_backend_event_synchronize` with a device-side
"D2H after the event wait" snapshot of the split boundary tensor — the same trick as `AIN_VERIFY` and
the same binary comparison.  If the boundary tensor is stale, the ordering hole is there and the fix is
a real event/stream dependency rather than a delay.

Second lead if H-A is negative: the *output* path.  `result_output` is a graph OUTPUT and the KLD is
computed from it; if it lives in pinned host memory written by the graph, then a host read before the
graph completes is a race with no stream ordering at all (the scheduler would need
`ggml_backend_sched_synchronize`, which is exactly `AIN_SYNC_INPUTS`' effect on the next step).
