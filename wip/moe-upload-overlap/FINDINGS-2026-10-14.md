# `moe-upload-overlap` — findings, 2026-10-14

**Verdict: the campaign's premise is refuted, but the thesis is not dead.**  `ggml_backend_meta_stage_input`
**does** engage on r62 (`e909c529a`) — the earlier "`n_host_inputs == 0` / `stage_input` never called"
reading was an instrumentation artifact.  The staged hand-off is worth **+41 %** over `GGML_SCHED_STAGE=0`
at `-ncmoe 4 -ub 4096`, so it is doing real work.  But the transfer is still essentially fully exposed:
`T(partial) = T(full) + bytes/rate` (8017 → 6586 t/s), forcing the staging copies onto the main stream
costs only ~5 %, and placing the 4 host layers FRONT/MIDDLE/BACK is a no-op (within 0.5 %).  The uploads
are pure async pinned 2-D H2D on the per-device copy stream (host issue 1–16 µs); what is missing is any
**lookahead**: the scheduler issues an upload only at the top of its own split, and the host is repeatedly
drained by graph-input host synchronizes introduced by the fragmented host-layer splits.

All numbers: gfx1201, 2× R9700, ROCm 7.14.1, `~/llama.cpp` r62 `e909c529a`,
`Qwen3.6-35B-A3B-Q8_0` (41 layers, 256 experts, 816 MiB routed experts/layer), `-sm tensor -fa 1 -t 8`,
`MOE_EXPERT_HEATMAP=0 MOE_EXPERT_CACHE_MIB=0`, `-p 4096 -n 0 -b 4096`.  Raw logs + the instrumentation
patch are in this directory.

## 1. THE UNRESOLVED GAP IS NOT REAL — `stage_input` engages

The seeding note claimed "in `sched_stage_issue` `n_host_inputs == 0` for every split ... and
`ggml_backend_meta_stage_input` is NEVER called".  With the correlation prints in place
(`tools/stage-trace-instrumentation.patch`, gated by `GGML_STAGE_TRACE=1`) the opposite is true:

* `sched_stage_issue` sees the tables: `SS split=2 … n_inputs=1 nhw=1 stage_enabled=1 bt=4096 mn=1542
  nnodes=1 n0_op=MUL_MAT_ID …`, `SS hostinput split=2 name=blk.0.ffn_gate_exps.weight … gatherable=0`,
  `n_host_inputs=1`.  The width gate **does not** misfire: `nodes[0]` is the `MUL_MAT_ID` and
  `sched_stage_batch_tokens` reads `bt=4096` (candidate **a** refuted); the split identity is right
  (candidate **b** refuted); `n_host_inputs` is 1, not > 8 (candidate **c** refuted — `GGML_SCHED_STAGE_SLOTS=16`
  is also a no-op, below).
* The function returns at `SS return split=2 reason=no_stage_buffer n_host_inputs=1` — because
  **the meta backend's `stage_buffer` is `nullptr` by design** (`ggml-backend-meta.cpp`: the meta backend
  stages per device via `stage_input`).  `stage_split_ok` was already set `true` before that return, so the
  hand-off still runs.
* `ggml_backend_sched_copy_input` confirms it: `CI split=2 input=blk.0.ffn_gate_exps.weight …
  stage_split_ok=1 stage_input=1`, then `CI … branch=stage_input took=1`, for **all 12 host tables**.
* `META_STAGE_INPUT … ret=1 chunks=2 slot=N`, and `META_GRAPH_COMPUTE … pending=1` shows `graph_compute`
  receiving the staged entries.

**Why the earlier reading was wrong:** the `n_host_inputs`/`stage_split_ok` bookkeeping happens *after* the
disabled/width-gate returns, and the meta backend intentionally has no `stage_buffer`, so a print placed at
a `return` (or read from a stale binary) reports zero.  The corrected correlation is the evidence above.

## 2. The upload path is already the "correct" one

`GGML_STAGE_TRACE=1` on the CUDA hooks (`ggml-cuda-moe-cache-hooks.cu`) shows every host table going
through the event-ordered ring:

```
CUDA_GATHER dev=0 path=pinned_2d n_copies=256 width=557056 stride=1114112 total=142606336 issue_us=16
CUDA_GATHER dev=1 path=pinned_2d n_copies=524288 width=272 stride=544 total=142606336 issue_us=2
```

* `path=pinned_2d` means `src_pinned=1` (the r15 pinned `ROCm_Host` source): a single
  `cudaMemcpy2DAsync` per device per table on `cuda_ctx->copy_stream()`, moving only the device's
  compacted half (136 MiB/device/table, 12 tables/pass).
* Host issue time 1–16 µs — the transfer is queued, not host-blocking.
* `graph_compute` then waits the per-slot `done` event and `stage_d2d`s the slot into the real split input
  on the main stream (device memory → device memory).

So the r62 fix (gather H2D moved to the main stream) concerns the **below-gate splice** path; the staging
path in this A/B was always on the copy stream.  The fix directions in the seed ("route through the ring",
"fix the gate", "raise the slots") are all moot: the ring/`stage_input` **already** carries the tables,
the gate passes, and 16 slots change nothing.

## 4. Why the transfer is additive — the host is drained per split

`GGML_STAGE_TRACE=1` timestamps (`logs/trace5-ncmoe4.out`, `logs/trace6-ncmoe4.out`) show the measured
pass issuing the first 9 tables within ~0.6 ms, then two large **host blocks**:

* `CI graph_input sync split=10 input=inp_pos sync_us=97757` (97.8 ms)
* `CI graph_input sync split=13 input=out_ids sync_us=42339` (42.3 ms)

These are the graph-input branch of `ggml_backend_sched_copy_input`: it calls
`ggml_backend_event_synchronize(sched->events[meta][cur_copy])`, a **host** wait for the meta event that
covers both devices and all queued GPU work.  They are introduced by the host-layer graph fragmentation:
the merged `down` splits (which carry the next layer's attention) and the big tail split carry host-written
graph inputs (`inp_pos`, `out_ids`, KV/attn index tensors), so the scheduler must drain before copying them.

Phase timing (`META_GC phase=done`, measured pass):

```
uid 282 (76 nodes)   total_us=672      uid 285 (100) total_us=199
uid 288 (100 nodes)  total_us=183      uid 291 (72)  total_us=193
uid 294 (3487 nodes) total_us=5925     (warmup had 98 / 30 / 11 / 196 ms)
```

So the host dispatch itself is cheap once warm; the front section is 141 ms of wall time
(588389 → 729759 µs), and ~140 ms of that is the two `ggml_backend_event_synchronize` drains.  The uploads
issued before/during those drains overlap *the drained GPU work*, but the structural order is fixed: for
FRONT the 12 uploads precede the bulk 3487-node compute; for BACK they follow it.  Because each upload is
issued only at its own split and there is no N+1 (let alone all-layers) lookahead, the total is additive in
either order — which is exactly why FRONT/MIDDLE/BACK are identical.

This matches the parked `wip/moe-layer-stagger/FINDINGS-2026-10-14.md` §3 conclusion ("issues split N's
upload at the top of split N's own iteration ... does not lead it, and there is no split N+1 prefetch"),
but the binding constraint is **not** the link (0.111 s of transfer vs 0.511 s of compute) — it is the
absent lookahead plus the per-split host drains.

## 5. What would actually make the overlap real

The copy-stream machinery is present and concurrent-capable; the missing pieces are scheduling:

1. **A real lookahead.**  Issue a host layer's table uploads several splits before the split that consumes
   them (ideally: at the top of the pass, or one host-layer ahead), so the per-device copy stream has
   in-flight device compute to run behind.  This is new code in the block-09 scheduler/meta path; it is the
   only lever that can hide the transfer.
2. **Remove/avoid the graph-input host drains** (`inp_pos`, `out_ids`).  Each is a full meta event
   synchronize that stops the host running ahead; without run-ahead a lookahead cannot be issued.
3. Placement alone cannot help (measured), and neither can ring depth (measured) — both are consistent
   with (1): the bytes still have to be issued *before* the compute they hide behind.

Ceiling: `max(total_compute, total_upload) ≈ max(0.511, 0.111) = 0.511 s` at `-ncmoe 4 -ub 4096`, i.e. up to
**~+22 %**; more at `-ub 2048` (the bill doubles).  It cannot beat the link.

**Not attempted here** (per the process rule: report before changing delivery code).  The owning blocks are
09 (scheduler/Meta) and 10 (`ggml-cuda.cu`).  A minimal prototype would be: a scheduler pre-pass that
`stage_input`s every host-weight split's tables up front (or one host layer ahead), with the existing
per-slot done/free events; then A/B `-sm tensor -ncmoe 4` FRONT vs BACK.  If BACK + lookahead ≫ FRONT, the
overlap is real and worth a block amendment; if not, the no-win is proven.
