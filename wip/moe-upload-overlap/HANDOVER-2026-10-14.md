## 0. TL;DR for the cold start

The campaign started as "make the host-expert H2D upload overlap compute" and that **failed as posed**
(the fetch already overlaps; an explicit prefetch just adds host cost — see `FINDINGS` §7).  The
campaign pivoted to the real finding: **`-ncmoe N` currently offloads the FIRST N layers; it should
offload the LAST N**, which is better on both prefill and decode.  That is implemented as a scratch-only
`LLAMA_NCMOE_FROM_END=N` loader rule and **wins on prefill (+4 % at `-ncmoe 20`)**, but **decode is
blocked by a slab-arming bug**: for the tail host set the movable-boundary slab declines to arm, the
expert cache falls back to a 816 MiB raw arena (6 of 60 tables), and decode collapses from ~87 to ~30 t/s.

**The next session's job is to find why the slab does not arm for the tail placement and fix it.**

---

## 1. Goal (frozen)

Make `-ncmoe N` host the **last N block indices**, `[n_layer - N, n_layer)`, generically — the last N
layers go to host, the rest stay on device.  Do **not** second-guess which of those layers are dense /
MoE / MTP / executed; just take the range (an expert override only ever matches a layer that has
`ffn_*_exps` anyway).  The appended MTP/nextn layers live at/after `n_layer`, so the range excludes them
by construction.  Rationale: the early layers carry the hotter / more-diverse expert routing, the tail is
cheaper to stream; and the tail has preceding resident compute to overlap the upload with.

Why this is the real prize (not the prefetch): the delivery default (`-ncmoe N` = first N) is the **worst**
placement measured on both axes; see §4.

## 3. Current scratch prototype (what is in the dirty tree)

Everything is env-gated and inert unless enabled.  The relevant pieces:

### 3a. The rear-fill rule — `src/llama-model-loader.cpp` (~line 1314, inside `create_tensor`)
Gate: `LLAMA_NCMOE_FROM_END=<N>`.  For an expert tensor whose block `tn.bid` is in
`[hparams.n_layer() - N, hparams.n_layer())`, it synthesizes a one-element `.*` override with a CPU buft
so the existing host-buffer selection runs unchanged.  It **skips the per-layer `blk.<i>` `-ncmoe`
patterns** (front-N) so the front is not also hosted.  A `NCMOE_TAIL host blk.<i> (n_layer=… N=…)` line
prints under `GGML_STAGE_TRACE`.  Verified: `LLAMA_NCMOE_FROM_END=20` + `-ncmoe 20` logs/hosts exactly
`blk.20..39` — and never `blk.40`.

### 3b. Supporting scratch instrumentation (prefetch campaign; not needed for the slab work)
- `common/common.h` + `tools/llama-bench/llama-bench.cpp`: the `LLAMA_NCMOE_LAYERS` / `_STRIDE` /
  `_OFFSET` / `_DEBUG` knob.  **Critical:** `llama-bench` does NOT call
  `llm_add_n_cpu_ffn_overrides` (it builds its own `n_cpu_moe` patterns), so the `common.h` knob alone is
  **inert for llama-bench**; the `llama-bench.cpp` change is what makes it work.  (Standalone copy:
  `wip/moe-layer-stagger/tools/ncmoe-layer-select.patch`.)
- `ggml-backend.cpp` / `ggml-backend-meta.cpp`: `GGML_SCHED_STAGE_PREFETCH` pre-pass + drain-by-split +
  phase timers (`COMPUTE_SPLITS …`).
- `ggml-cuda-moe-cache-hooks.cu`: `GGML_STAGE_NOCOPY` (timing-only, skips the H2D) + a `GATHER` trace.
- `ggml-cuda.cu`: `GGML_CUDA_BIGTIME` GPU-event timer.  **WARNING: this timer creates CUDA events during
  CUDA-graph capture and SIGABRTs (the 2× 3.2 GB coredumps).  Do NOT enable `GGML_CUDA_BIGTIME`; delete
  or gate it to `!use_cuda_graph` before using it.**

## 5. THE BLOCKER — the slab does not arm for the tail placement

`llama-bench … -ncmoe 20 -p 512 -n 500 -b 4096 -ub 512 -r 1 -v` with `LLAMA_NCMOE_LAYERS=20..39`:

```
moe_cache_init: MoE expert cache enabled on device 0: budget=4096 MiB/device, period=32 steps, defer…
alloc_all_locked: the MoE expert cache is enabled but the movable-boundary slab is NOT armed; the arena
                  is a raw cudaMalloc and a wide prefill can abort (the pre-slab failure mode, issue #136).
alloc_table_locked: layer=39 role=blk.39.ffn_gate_exps.weight is FULLY RESIDENT (256/256 slots) …
alloc_all_locked: per-device sizing: 2 device(s), arena total 816.0 MiB
moe_cache_report: … tables=6 slots=1536 arena=816.0 MiB (budget 4096 MiB/device)
```

With `LLAMA_NCMOE_LAYERS=19..38` the same command logs the full `tables=60 … arena=4080.0 MiB` and hits
86.8 t/s.  Saved log: `logs/slab-not-armed-2039.txt`; the `llama-cli` (works) log:
`logs/cli-2039-512prompt.txt`.

**Where to look (the arm chain):**
- `ggml/src/ggml-cuda/ggml-cuda-slab.cu` — `g_slab_armed` (line ~167);
  `ggml_cuda_slab_enabled()` (~404) = `slab_env() != 0 && g_slab_armed`;
  `ggml_cuda_slab_arm()` (~1095) just sets `g_slab_armed = true`; `ggml_cuda_slab_min_arena_bytes()` (~295,
  `GGML_CUDA_SLAB_MIN_ARENA_MIB`, default 2048) and the "work + floor" creation test.
- `ggml/src/ggml-cuda/ggml-cuda.cu` — `ggml_backend_cuda_device_moe_cache_preflight` (~6192): calls
  `moe_cache_preflight(...)`; **only if it returns true** does it call
  `ggml_cuda_slab_set_ring_region(...)` and `ggml_cuda_slab_arm()`.
- `ggml/src/ggml-cuda/moe-expert-cache.cu` — `moe_cache_preflight` (~2665).  Note: with an **explicit**
  `MOE_EXPERT_CACHE_MIB` it returns `true` early (`if (!g_auto) return true;`), so on paper the arm should
  happen regardless of the floor.  The `NOT armed` warning is emitted in `alloc_all_locked` (~2267) when
  `!g_tables.empty() && !ggml_cuda_slab_enabled() && ggml_cuda_slab_configured()`.
- Caller chain from libllama: `llama_model_moe_cache_preflight` (only for a non-empty host-expert map).

**Hypotheses to discriminate (do these in order):**
1. **Is `ggml_backend_cuda_device_moe_cache_preflight` even called for the tail set?** Add a print / break
   in it; compare a `19–38` run (arms) vs `20–39` (does not).  If it is not called, the host-expert
   detection / map build differs — find where `moe_host_expert_bytes` / `max_host_table_bytes` is computed
   (`src/llama-model.cpp` / the loader) and why the tail changes it.
2. **Does `moe_cache_preflight` return false?** (i.e. `g_enabled` false at preflight time, or the
   `g_min_res_pct` / auto floor rejected it).  Even with explicit MIB the first `if (!g_enabled)` can
   return false before env parse — check the `ensure_env()` ordering and whether the preflight runs before
   `moe_cache_init`.
3. **Does `ggml_cuda_slab_arm()` run but `ggml_cuda_slab_configured()`/creation fail later?** The slab is
   created before the weights; check `ggml_cuda_slab_extend` / the `work + floor` test and whether the
   *resident* layer set (which differs when blk.39 vs blk.19 is resident) changes the free-VRAM estimate
   at creation.  blk.39 is a full-attention layer (bigger attn tensors than the GDN layers), so the
   resident set differs in *bytes* between the two placements even though both host 20 layers.
4. **A/B the workaround to isolate allocation vs placement:** run `20–39` with
   `GGML_CUDA_SLAB_MIN_ARENA_MIB=0` (or a tiny value) and with a larger `GGML_CUDA_SLAB_RESERVE_MIB`; if the
   slab then arms and decode recovers, it is the work+floor creation test, and the fix is to make that
   test placement-robust (or to size the reserve from the actual host-expert bytes).
5. Confirm with `llama-cli` (which arms) vs `llama-bench` (which does not) what differs in the context
   creation order — that difference is the cleanest repro harness.

**Do NOT** "fix" it by disabling the slab, and do not ship rear-fill until the cache arms for both
`19–38` and `20–39` with equal cache residency.

## 6. Corrections / pitfalls (do not repeat these)

- **`llama-bench` ignores the `common/common.h` `LLAMA_NCMOE_LAYERS` knob.**  The knob patch must also
  change `tools/llama-bench/llama-bench.cpp` (the prototype does).  Every earlier "placement is a no-op"
  number that used the standalone `ncmoe-layer-select.patch` with `llama-bench` was **inert**.
- **Byte-confounded A/Bs.**  `0,1,2,3` is 4 layers (12 tables) but `36,37,38,39` is 3 (9 tables) because
  the tail requests hit the MTP/… — always verify the staged/loaded set with the `STAGE_OK` (or
  `NCMOE_TAIL`) trace before comparing.  The first "BACK +5.7 %" and the first "3-layer" result were both
  confounded.
- **`blk.39` is NOT dense.**  It has `ffn_*_exps`; it is a full-attention trunk layer.  The staging trace
  showed it not executing in a plain `-n 0` prefill, which is an execution artifact, not density.
- **The prefetch is a dead end.**  The staged hand-off already engages (`stage_input took=1`); an explicit
  all-up-front prefetch reduces GPU kernel time but adds ~14 ms/pass of host cost and is ~4 % slower.  See
  `FINDINGS` §7.  Do not re-chase it.
- **Do not `GGML_CUDA_BIGTIME`** (SIGABRT during graph capture); **do not run parallel benches**; always
  `timeout`; `llama-cli` always `--single-turn`.
- The `MOE_EXPERT_HEATMAP` sidecar exists next to the model; keep it OFF for these A/Bs.

## 10. Copy-paste repro harness

```bash
M=/llm/models/Qwen3.6/35B-A3B/Q8_0/Qwen3.6-35B-A3B-Q8_0.gguf
B=~/llama.cpp/build-rocm-hybrid/bin/llama-bench
C="MOE_EXPERT_HEATMAP=0 HIP_VISIBLE_DEVICES=0,1 LD_LIBRARY_PATH=/opt/rocm-7.14.1-gfx120X/lib"
FRONT=$(seq -s, 0 19); TAIL=$(seq -s, 20 39)

# prefill — rear wins:
for L in "$FRONT" "$TAIL"; do env $C MOE_EXPERT_CACHE_MIB=0 LLAMA_NCMOE_LAYERS="$L" $B -m $M \
  -ngl 99 -sm tensor -ncmoe 20 -p 4096 -n 0 -b 4096 -ub 4096 -r 3 -t 8 -fa 1 -o md; done

# decode — rear COLLAPSES (slab not armed); add -v and grep 'slab|tables=':
env $C MOE_EXPERT_CACHE_MIB=4096 LLAMA_NCMOE_LAYERS="$TAIL" $B -m $M -ngl 99 -sm tensor -ncmoe 20 \
  -p 512 -n 500 -b 4096 -ub 512 -r 1 -t 8 -fa 1 -o md -v 2>&1 | grep -E "tg500|slab is NOT armed|tables=[0-9]+ slots"
# control (arms, ~87 t/s):  same with TAIL -> $(seq -s, 19 38)

# the new loader rule (scratch):
env $C MOE_EXPERT_FROM_END=20 LLAMA_NCMOE_FROM_END=20 $B -m $M -ngl 99 -sm tensor -ncmoe 20 \
  -p 4096 -n 0 -b 4096 -ub 4096 -r 3 -t 8 -fa 1 -o md
```
