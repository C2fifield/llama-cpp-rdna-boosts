# `moe-upload-overlap` — the decode blocker, root-caused and fixed (2026-10-14)

**Status: the decode blocker is FIXED in scratch and the matched A/B now has `rear >= front` on both
axes.  This is WIP: nothing here is in `patches/` and nothing has been applied to the fork branch.**
This supersedes the "the slab does not arm for the tail placement" framing in
`HANDOVER-2026-10-14.md` §5 / `FINDINGS-2026-10-14.md` §8 — the slab is a red herring (it is a *second*,
independent llama-bench-only gap).  The actual blocker is a **premature arena-sizing latch** in
`moe-expert-cache.cu`.

**Follow-up (maintainer decisions, same day):** the preflight now lives in `llama_model_load_from_file`
(universal); the fix is cut for **block 09** as `tools/block09-cache-sizing-and-preflight.patch`; and the
`-sm layer` "regression" was investigated and does not reproduce (it was a single-rep artifact).  MTP was
re-run on the 35B embedded head (`none == n3`, bit-identical) and on the GSQ-RCO Qwen3.8-Flash-Next model
with its separate MTP head (coherent, front == tail).

## 1. TL;DR

Two independent bugs make `llama-bench` measure the tail placement as a decode collapse while
`llama-cli` is fine:

1. **`llama-bench` never calls `llama_model_moe_cache_preflight`.**  It bypasses
   `common_init_from_params` (it calls `llama_model_load_from_file` + `llama_init_from_model`
   directly), and the preflight is the only caller of `ggml_backend_cuda_device_moe_cache_preflight`,
   the only thing that arms the movable-boundary slab.  So under `llama-bench` the slab is **never**
   armed for *any* placement (front included) — it is not a tail-specific arming failure.
2. **The arena sizing latches on a partially-registered table set.**  `alloc_all_locked()` sizes the
   arena from the tables registered *so far* and sets `g_sized = true`.  A table that registers
   afterwards never gets an arena.  During a prefill the bulk host-weight upload is served by the H2D
   staging ring, which does **not** register cache tables; a non-staged 1-token tail ubatch reaches the
   decode hook and primes only the **last** host layer.  `llama-bench` runs two prefill passes
   (warmup + measured) before any decode, so the second pass triggers the sizing against those 6
   tables (one layer), the arena is capped at 816 MiB / 6 tables, and the decode collapses.
   `llama-cli` does one prefill pass, so the first decode registers all 20 host layers and sizes
   correctly — which is why the CLI "arms fine".

The fix (`tools/block09-cache-sizing-and-preflight.patch`, block 09; the placement rule itself is the
separate `tools/rear-fill-prototype.patch`) has two parts:

1. **Universal preflight.** `llama_model_load_from_file_impl` now calls
   `llama_model_moe_cache_preflight` (moved here from `common_init_from_params`, which `llama-bench`
   never reached).  The load-time call arms the slab and records the expected host-expert bytes for
   *every* consumer; `common` still calls it again with the draft/MTP aux estimate, and the early auto
   floor **re-runs when the aux grows** (a bigger aux can only decline, and a declined later call
   **disarms** the slab again so a cache-off run does not withhold an unused arena).
2. **Robust deferred sizing.** The arena sizing now waits until the registered host tables account for
   the per-device bytes the preflight reported (`moe_cache_tables_complete_locked`), and a table the
   cache can never hold is subtracted from that expected total so the wait can always complete.

With both, both placements reach **full residency (60 tables / 4080 MiB per device)** and the tail wins
on both axes.

## 2. Root cause, step by step (the 5 hypotheses from HANDOVER §5)

Worked with `GGML_CACHE_REG_DEBUG`/`GGML_CACHE_REG_BT` scratch prints in `moe-expert-cache.cu`
(backtrace, per-table registration, sizing), `MOE_EXPERT_CACHE_MIB=4096`, heatmap OFF.

* **(a) Is the preflight called for the tail set?  No — for *any* set, under `llama-bench`.**
  `grep` of the callers of `llama_model_moe_cache_preflight` is `common/common.cpp:1383` only
  (plus a test).  `llama-bench` never calls it.  The first A/B of this session (before any change)
  reproduces it directly: `llama-bench … -p 512 -n 20 -v`, `MOE_EXPERT_CACHE_MIB=4096`, logs
  `the MoE expert cache is enabled but the movable-boundary slab is NOT armed` and no `SLAB_INIT` for
  **both** `LLAMA_NCMOE_LAYERS=19..38` (the arm the HANDOVER §5 called "works") and `20..39` —
  `19..38` only *looks* fine because its raw `cudaMalloc` arena happens to reach 4080 MiB there.
  After adding the one-line call, `SLAB_INIT` appears for both placements.
* **(b) Does `moe_cache_preflight` return false?  No.**  With an explicit `MOE_EXPERT_CACHE_MIB` it
  returns `true` early (`if (!g_auto) return true;`).  The cache is enabled.
* **(c) Does `ggml_cuda_slab_arm()` run but creation decline?  Not the cause here.**  Once the
  preflight runs, `SLAB_INIT` shows the slab created (`size(VA)=18.31 GiB`, `boundary=0.75 GiB`,
  `ring_req=4.03 GiB`).  The tail decode still collapses — because of the sizing latch, not the slab.
* **(d) `GGML_CUDA_SLAB_MIN_ARENA_MIB`/`RESERVE_MIB` are not it.**  With the slab armed the arena still
  sized to 3 tables/device; the slab's capacity was available (18 GiB) but `alloc_all_locked` sized
  from the registered subset.
* **(e) The llama-cli vs llama-bench difference is the pass sequence, not the slab.**  With the backtrace
  print, the 1-token hook for `blk.39` comes from `llama_context::process_ubatch` (a real 1-token
  ubatch).  `llama-cli` runs one prefill then a decode: the decode's first pass registers layers
  `20,21,…` in order and only then does the sizing fire with all 20.  `llama-bench`'s `pp` test runs
  **two** prefill passes (warmup + measured): pass 1 primes `blk.39`, pass 2 hits the primed table and
  calls `alloc_all_locked()` with 6 tables registered.

Evidence (tail, `-p 64 -n 20 -uv 512`, before the fix, slab armed via the added preflight):

```
alloc_all_locked: device 0: sized 256 slots/table from 3 tables / 1.6 MiB per expert (budget 4096 MiB/device)
alloc_all_locked: per-device sizing: 2 device(s), arena total 816.0 MiB
moe_cache_report: device 0: tables=3  slots/table(sum)=768  arena=408.0 MiB
moe_cache_report: device 1: tables=3  slots/table(sum)=768  arena=408.0 MiB
| ... tg20 | 23.34 |
```

The `alloc_all_locked` call site is `moe_cache_update_host` (`if (!t.primed) { t.primed = true; return
false; }  … if (!g_sized) { if (n_tok <= 8) alloc_all_locked(); }`), i.e. the deferred sizing assumes
the priming pass registered *every* table.  A partial pass violates that assumption.

## 3. The fix

`tools/block09-cache-sizing-and-preflight.patch` (self-contained; seven files:
`ggml-cuda/moe-expert-cache.cu`, `ggml-cuda/ggml-cuda-slab.cu`, `ggml-cuda/ggml-cuda-vmm.h`,
`ggml-cuda/ggml-cuda.cu`, `ggml-backend-meta.cpp`, `src/llama-model-loader.cpp`, `src/llama.cpp`):

* **`src/llama.cpp`:** `llama_model_load_from_file_impl` calls `llama_model_moe_cache_preflight(model,
  aux)` after a successful load, with `aux = params.load_mtp ? MOE_EXPERT_CACHE_AUX_RESERVE_MIB_DEFAULT
  : 0` (`common` sets `load_mtp` from the spec type, so the separate `-md` MTP head is covered too).
  This is the universal arm.
* **`moe-expert-cache.cu`:** `moe_cache_preflight` records the per-device `host_expert_bytes` in
  `g_preflight_device_bytes[]`/`g_preflight_device_seen[]` (before the explicit-budget early return,
  so it works for `MOE_EXPERT_CACHE_MIB=4096` too), using `max` so a second model cannot lower the bar;
  and the auto floor re-runs when a larger aux arrives (`g_preflight_aux`).
* **`moe_cache_tables_complete_locked()`:** sums `n_experts * expert_bytes` over the registered tables
  per device and returns false while any seen device is short of its expected bytes.  Unseen devices /
  an absent preflight are treated as complete.  `alloc_all_locked()` sets `g_sized = true` only when
  complete; otherwise it returns and a later decode-band pass re-enters.
* **`moe_cache_note_unregisterable()`** subtracts a table the cache can never hold (an unaddressable
  split slice) from the expected bytes, keyed on `(weight->data, device)`, so the wait cannot deadlock.
* **`ggml_cuda_slab_disarm()`** (slab + vmm + cuda.cu) undoes a previous arm when the better-informed
  (larger-aux) preflight declines the cache.
* **`-lm none` + `-sm tensor` (two fixes, see §4h):** `src/llama-model-loader.cpp` uses whole-tensor
  uploads for the Meta device instead of the chunked pinned pipeline (a mid-row 1 MiB chunk cannot be
  expressed by the Meta splitter), and `ggml-backend-meta.cpp` tightens
  `ggml_backend_meta_set_tensor_async`'s sync fast path to `size % row_stride == 0` (or the axis-1
  `<=512`-byte MMQ tail pad) so a mid-row chunk is accumulated rather than asserted/corrupted.

`common_init_from_params` keeps its preflight call: it is now the aux *refinement*, not the armer.

### 4h. `-lm none` + `-sm tensor` model-load abort — root cause, regression window, FIXED

**Symptom.** `-lm none` (`LLAMA_LOAD_MODE_NONE`) + `-sm tensor` + `-ncmoe` aborts at
`ggml/src/ggml-backend-meta.cpp` (`GGML_ASSERT(size % row_stride == 0)` in
`ggml_backend_meta_buffer_set_tensor`, axis-0 segmented split), **during model load**, before any
context or preflight.  `-lm auto`/`-lm mmap` are fine.  Reproduced on the 35B-A3B Q8_0, the delivery
`/llm/models/Qwen3.8/Flash-Next/IQ3_XXS`, and the GSQ-RCO model.

**Root cause.** `-lm none` disables mmap, so the loader takes its **chunked pinned async-upload** path
(`src/llama-model-loader.cpp`): 1 MiB pieces uploaded via `ggml_backend_tensor_set_async`.  Under
`-sm tensor` the upload backend is the **Meta** device, and a 1 MiB piece is not a multiple of a
quantized tensor's row stride (e.g. `blk.0.ssm_out.weight`, q8_0, `nb[1]=4352`: `1 MiB % 4352 = 4096`).
Block 09's segmented path accumulates mid-row chunks and flushes whole, but its sync fast path was
`offset % row_stride == 0` **without a `size` check**, so the loader's first chunk (`offset=0`) was
dispatched to `ggml_backend_meta_buffer_set_tensor`, whose axis-0 path asserts `size % row_stride == 0`.

**Regression window (how the earlier gates passed).** `git log -G "row-aligned range"` on
`patches/0009-*.patch` shows the sync fast path was added by **r54** (*"segmented host-resident expert
upload fixed, gemma4 `-sm tensor` rejection lifted (block 09)"*).  The last green qwen4exp gate is
**r53** (and r41/r50/r51 before it) — block 09 handled the loader chunks correctly then.  The r54 entry
in `WORKLOG.md` describes the upload change but **does not record a qwen4exp-gate re-run**, so the
regression was promoted without the gate that would have caught it.  (That is the answer to "how did the
gate pass though broken": the gate was not re-run on the r54 change; the `-lm none` path was only
exercised by it.)

**Fix (both in block 09).**
* `src/llama-model-loader.cpp`: the Meta device uses whole-tensor uploads (never the 1 MiB chunked
  pipeline); the async overlap is lost only on the non-mmap `-sm tensor` path.
* `ggml-backend-meta.cpp`: `ggml_backend_meta_set_tensor_async`'s sync fast path now also requires
  `size % row_stride == 0` (or the axis-1 `<=512`-byte MMQ tail pad), so any other caller's mid-row
  chunk is accumulated rather than asserted/corrupted.

**Verification.**

| check | before | after |
|---|---|---|
| 35B `-lm none -sm tensor -ncmoe 0` | SIGABRT | rc=0, `-lm none` == `-lm auto` (`47 chars sha=49bf8044ec4b`) |
| `gate-qwen4exp-quant-coherence.sh` (IQ3_XXS) | SIGABRT | **PASS** (0 `////`, gather ON == OFF `249787803687`) |
| gate (IQ4_NL) | — | **PASS** (`54ee6ea0893e`) |
| gate (Q4_K_M) | — | **PASS** (`16d7957b2c0f`) |
| GSQ-RCO + separate MTP head, `-lm none`, `-ub 4096` | SIGABRT | `////`=0, bit-identical to `-lm auto` (`662 chars sha=34460ed5851b`) |

The Q4_K_M arm initially OOM'd (rc=137) purely because the 74 GB GSQ model was resident in `/tmp`
(tmpfs); with it removed the arm passes.  The gate remains green with the whole-tensor path — the
gather ON == OFF hashes are unchanged from the pre-`-lm none` runs.

## 7. Open questions / resolved decisions

1. **Preflight location — RESOLVED (maintainer): universal, in `llama_model_load_from_file`.**
   Implemented: the load-time call arms the slab and records expected bytes for every consumer; `common`
   refines the aux and the auto floor re-runs on a larger aux (with disarm if it then declines).  The
   one behaviour change vs the old common-only ordering is that the floor's first pass sees `aux = 0`;
   the re-run restores the with-draft answer.
2. **Block ownership — RESOLVED (maintainer): block 09.**  `block09-cache-sizing-and-preflight.patch`
   is cut against r62 (and applies after the placement prototype).
3. **`-sm layer` tail prefill — RESOLVED: no regression** (see §4c; the earlier number was a single-rep
   artifact).
4. **`-lm none` model-load abort — RESOLVED (see §4h).**  Root cause: the r54 block-09 sync fast path
   misrouted the loader's mid-row chunks.  Fixed in the loader (Meta = whole-tensor upload) and the
   meta async fast path; the qwen4exp gate is green again.  The r54 promotion skipped the gate re-run.
5. **Deferral cost.**  The deferral adds one eager pass before sizing; `moe_cache_ready()` already gates
   graph capture on `g_sized`, so this is not a new capture stall, but a **prefill-only** workload never
   sizes the arena (harmless: the arena is decode-only).  Confirm no perf regression on the server
   first-turn path.
6. **Dedup the placement mechanism.**  The delivery should carry a real `llama_model_params` field
   (HANDOVER §8), not `LLAMA_NCMOE_FROM_END`; the block-09 patch is independent of that plumbing.
