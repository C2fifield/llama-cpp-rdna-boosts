## 1. TODO #68 — Gemma4 dense + `-sm tensor` aborts (two distinct defects)

Both are **pre-existing** (reproduce on the unmodified r99 and r100 trees, and on a `build-r99` binary).
Neither involves the #77 work.  `-sm layer` is unaffected, which is why every other gate in this campaign
ran there.

### 1a. Rotated K/V cache (`-ctk q8_0 -ctv q8_0`) — `unsupported mul_mat split states`

```
ggml/src/ggml-backend-meta.cpp:901: unsupported mul_mat split states:
  node=node_286 src0=Meta(ROCm0,ROCm1)#attn_inp_k_rot#0 axis=10 src1=Kcur_pos-5 (reshaped) axis=0
```

Repro (2 minutes, no draft model):

```bash
cd ~/llama.cpp && HIP_VISIBLE_DEVICES=0,1 ./build-rocm/bin/llama-cli \
  -m /llm/models/Gemma4/12B/Q8_0/gemma-4-12b-it-Q8_0.gguf \
  -ngl 99 -sm tensor -ctk q8_0 -ctv q8_0 -p "The capital of France is" -n 8 \
  --seed 42 --temp 0 --no-display-prompt --single-turn -t 8
```

`attn_inp_k_rot` is the K rotation matrix (`llama_kv_cache::build_input_k_rot`, built only when
`n_rot_k > 0`), so the aborting op is `ggml_mul_mat(rot, Kcur)` with `src1` (Kcur) split on **axis 0** — a
pair `handle_mul_mat` does not implement (`src0` is MIRRORED, `src1` is axis-0 split; the handler covers
MIRRORED/MIRRORED, axis1/MIRRORED, MIRRORED/axis1, axis0/axis0, equal-axis>=2, axis>=2/MIRRORED).
Independent of `-np`, `--kv-unified`, `-fa` and of the CUDA-side rope switches (this is a Meta graph op).

**Direction (unchanged from the TODO entry):** teach `handle_mul_mat` the (MIRRORED, axis-0) rotation
pair — correct and small, but check the *cost*: a MIRRORED `rot` (256x256 F32) against an axis-0-split
Kcur means every device must hold the whole rotation matrix and produce a full row block for its own
column slice, i.e. a partial reduction across devices for the output rows.  `GGML_BACKEND_SPLIT_AXIS_PARTIAL`
exists in the enum for exactly this, but every consumer of a PARTIAL input must handle it (check who
does).  Alternatives: rotate **after** the split gather (a per-device copy of the gather output), or
express Kcur for the rotation as MIRRORED (it is small at decode: 1 head-dim row per token), or reject
`-sm tensor` + a rotated cache type at params level with a clear message (the DFlash-style honest interim
from #78).  Start with the *diagnosis*: print `n_rot_k`/`n_rot_v` and the split state of `Kcur` at graph
build, and decide which of the four shapes the rotation really needs.

### 1b. Default f16 cache — `GGML_ASSERT(src_ss[0].axis != GGML_BACKEND_SPLIT_AXIS_0)` in `handle_per_row`

Found 2026-10-21 while running the #76 gates; **not** in the TODO entry yet (added there this session).

```bash
cd ~/llama.cpp && HIP_VISIBLE_DEVICES=0,1 ./build-rocm/bin/llama-cli \
  -m /llm/models/Gemma4/12B/Q8_0/gemma-4-12b-it-Q8_0.gguf \
  -ngl 99 -sm tensor -p "The capital of France is" -n 8 \
  --seed 42 --temp 0 --no-display-prompt --single-turn -t 8
# -> ggml-backend-meta.cpp:838: GGML_ASSERT(src_ss[0].axis != GGML_BACKEND_SPLIT_AXIS_0) failed
#    (aborts at the warmup decode, i.e. AFTER the graph builds and the model loads)
```

So `gemma4` dense + `-sm tensor` is broken **regardless of cache type**; #68 as filed only covers the
rotated-cache half.  `-fa off` is not an option (`SPLIT_MODE_TENSOR requires flash_attn to be enabled`),
`-c 4096` does not help, and `-ctk f16 -ctv f16` changes nothing.

`handle_per_row` is used by `NORM`, `RMS_NORM`, `RMS_NORM_BACK`, `GROUP_NORM`, `L2_NORM`
(`ggml-backend-meta.cpp:1246-1250`) and by `ARGSORT`/`TOP_K` (`:1332`).  It asserts because the op's input
is split on axis 0, i.e. split **inside the row it reduces over** — the reduction the op performs is
genuinely cross-device.  Gemma4 runs a per-head RMS norm (`q_norm`/`k_norm`) over `head_dim`; under
`-sm tensor` the attention heads are split, and after the reshape the head axis becomes axis 0 of the norm
input — which is why the assert fires for this arch and not for the Qwen models.

**Direction:** a per-head norm over a head-split axis is a *local* reduction, not a cross-device one — each
device holds whole heads, so the correct fix is to teach the Meta split state that a RESHAPE which folds
`head x head_dim` into one axis keeps the split **compatible with the reshape** (the split boundary falls
on a head boundary), and then let `handle_per_row` accept an axis-0 split whose segments do not straddle a
row.  Concretely: check `ggml_backend_meta_split_state`'s reshape handling for `axis == 0` with
`n_segments > 1` (it asserts `src_ss[0].n_segments == 1` in the axis-2/3 cases, see `:1007`/`:1025`), and
add the "seamless" case where every segment is a whole number of rows.  If that turns out to be wrong for
a norm that really does reduce across the split (e.g. a hidden-dim RMS_NORM on a hidden-split tensor),
then the honest interim is the same as 1a: reject with a clear message.

**Both halves are worth doing together**: they are the same subsystem (Meta split-state predicates) and a
fix for one usually needs the other's test shape.

## 2. PRIORITY 1 — MTP must be run-to-run deterministic (maintainer decision, 2026-10-21)

Measured this session (`evidence/MEASUREMENTS-2026-10-21.md` §4).  With host-resident experts
(`-ncmoe 40`) + an active expert cache + MTP + captured HIP graphs, the greedy text differs between two
identical runs (`8241a94d2f86` vs `afa48a6ea28a`).  Deterministic when **any** of these is changed:
`GGML_CUDA_DISABLE_GRAPHS=1` (and then it also equals plain decode), `GGML_CUDA_ASYNC_INPUT=0`,
`-ncmoe 0` (no host experts), `MOE_EXPERT_CACHE_MIB=0`, or `--spec-draft-n-max 2` instead of 3.

That is the r69 / TODO #75 class (a captured graph replayed while a host-resident input buffer is being
rewritten), not a new defect: on r99 the same MTP run is deterministic only because the cache never
sized, i.e. the per-op upload path it took has no residency state to race.

**Requirement (maintainer):** two identical runs of the same config must produce the same text **by
default** — not behind `GGML_CUDA_DISABLE_GRAPHS=0`-style workarounds.  A kill switch that restores the
nondeterministic arm is acceptable for bisecting; shipping the workaround as the default is not.  The bar
for the fix is the same instrument the delivery already trusts: N identical fresh-process runs, plus
`test-logits-width-probe` where the shape allows it (and, per `WORKLOG.md` 261020.014, hash with
`scripts/extract-generated.py`, never a raw terminal slice).

Entry points for the next session:

* `moe_cache_update_host` stages `t.remap_dev` with an **async** H2D from the persistent `t.remap_host`
  (the comment claims "the scheduler synchronizes the backend before the next hook" — verify that under
  MTP, which issues several `llama_decode` calls per token and may not).
* The identity fast path (`slots == n_experts`) passes raw ids and the arena base, so it stages nothing
  per token; the cache report showed `takeover=0`, `get_ok>0`, `h=0` — confirm which path each of the two
  divergent runs actually used before chasing the staging.
* A `-n 300` reproduction takes ~90 s (5298-token prefill dominates).  Two runs are enough to see it.
* Suggest `GGML_CUDA_FUSE_CPY_BATCH_DEBUG=1`-style instrumentation only after the two runs are shown to
  differ on the *same* code path.
* Note the r90 fix in the same family: `set_tensor_async`/`set_tensor_2d_async` now snapshot through the
  pinned upload ring **unconditionally**, because a caller's live host pointer could be rewritten before a
  queued copy ran.  The cache's own staging (`t.remap_host` -> `t.remap_dev`) is the analogous shape and
  has no such snapshot; check whether MTP breaks the "the scheduler synchronizes before the next hook"
  assumption the comment relies on.
* Second candidate: the *draft* context and the target share the process-wide cache and `g_alias_to_id`
  (keyed by the device tensor pointer, overwritten per hook).  Under MTP two graphs (target verify,
  draft decode) can hold the same reused allocator address; if the alias lookup resolves to the wrong
  table for one of them, the op reads another layer's arena.  `moe_cache_get_table`'s semantic fallback
  (`g_sem_to_id`) exists for exactly this — verify it is *always* correct rather than preferred.

**Definition of done:** the §4 reproduction is identical across 6+ fresh processes with graphs on, the
`-n 3000` P-axis text is identical across 3 runs, `none == draft-mtp` holds at `n_max <= 7` on gemma4
(MoE is exempt from byte identity vs *plain* but MTP's own run-to-run stability is not negotiable), and the
35B-A3B / 27B 4-axis gates are unchanged.

2. **`--fit` under-arms the arena when a second context exists — DECIDED: investigate and fix** (§0.3).
   At the default context the draft + target contexts make `--fit` reserve 19.16 GiB/device, the slab is
   created at only 9.31 / 7.50 GiB and the arena at 13.8 GiB instead of 23.1: `h=0.907`, 8030 cold reaches,
   and MTP falls to **50.2 t/s against plain 79.3**.  Pinning `-c` hides it, which is not a fix.

   Facts to start from: the slab reports **18.25 GiB of "VA spare for `ggml_cuda_slab_extend`"**, so the
   capacity exists but the arena sizing latched before it was mapped (`alloc_all_locked` sizes from
   `ggml_cuda_slab_arena_total(d)` and calls `ggml_cuda_slab_extend_all()` only when `!g_alloc_priming`;
   `g_sized` then never re-evaluates).  Candidate directions, cheapest first:
   (a) when the arena is *clamped by slab capacity* and the slab still has VA spare, extend before sizing
   (does that collide with the r75 finding that the prime sizing must not map the reserve under a live
   wide-prefill work view? check `GGML_COMPUTE_BUFFER_MARGIN_PCT`-era reasoning);
   (b) a bounded, one-shot **grow** pass after the post-prefill drop (`moe_cache_rearm` already exists and
   keeps layer-uniform slots — can it take a larger slot count without breaking the layer uniformity
   invariant, the fusion guard, or a captured graph?);
   (c) make `--fit` reserve the *cacheable* expert bytes rather than the auto floor, so a 23 GiB expert set
   is not squeezed to a floor sized for a smaller one;
   (d) check the draft context's KV accounting in `common_params_fit_impl` — 19.16 GiB of reserve on a
   32-GiB card looks like the fit is sizing two max-length contexts.
   Whichever is chosen must keep the invariants in `AGENTS.md` ("A compute buffer that cannot grow must
   never abort; the MoE arena is what yields", the wholesale-fallback rule, and no arena freed while a
   kernel carrying its address is in flight).
3. **`--spec-draft-n-max 2` looks like the sweet spot for the Gemma4 drafter** (86.2-86.3 t/s vs 85.3 at
   n3, and deterministic where n3 was not).  Worth a proper 4-axis run before any recommendation.
4. `MOE_EXPERT_CACHE_SLOTS` remains the fastest way to A/B an arena sizing question; remember it also
   bypasses `alloc_all_locked`'s completeness gate entirely (that is why it made the pre-fix numbers
   look good).
